# Modulo Information Intake ↔ Noesis

This is the initial signed-in bridge for [Modulo #474](https://github.com/Ikey168/Modulo/issues/474) and [Noesis #1569](https://github.com/Ikey168/Noesis/issues/1569). Install the **Information Intake** workspace plugin. The plugin calls Modulo's `/api/integrations/noesis/intake` facade, which opens a new authenticated Noesis Streamable HTTP MCP session per request. The browser never receives a Noesis token. The existing Noesis Daily Brief Blueprint plugin remains a separate, read-only input.

## Configuration and identity

Set `NOESIS_INTAKE_MCP_URL` to the Noesis Knowledge Engine `/mcp` endpoint and `NOESIS_INTAKE_CREDENTIALS_FILE` to a server-only JSON file. HTTPS is required except for a loopback HTTP endpoint. The bridge does not follow redirects or use environment proxies. Give the credentials file owner-only permissions on a POSIX filesystem (`chmod 600`). Its keys are Modulo's authenticated numeric user IDs:

```json
{"1":{"token":"the-per-user-noesis-bearer-token"}}
```

Configure Noesis's `NOESIS_MCP_AUTH_TOKENS_FILE` with the same token mapped to one unique `client_id` and the required `knowledge:intake:*` and `namespace:<name>:*` scopes. Decision Support also needs `knowledge:decisions:read` and `knowledge:decisions:write`; a standalone decision does not need project access. The Noesis `client_id` is the owner of Noesis intake sessions, feed items, and decisions. Modulo selects a token only from its authenticated user ID, never from a request argument. A missing mapping, unavailable Noesis, or an unsupported tool produces an explicit preflight/bridge error. The bridge allowlists intake and decision tools; Noesis enforces namespace and object access on every call. `knowledge:intake:fetch` is needed for feed refresh and live Exploration page acquisition.

## Current authority and mapping

| Modulo object or field | Noesis object or field | Authority |
| --- | --- | --- |
| Signed-in user and plugin installation | Per-user MCP token and Noesis intake owner | Modulo authenticates; Noesis authorizes its objects |
| Plugin preference `namespace` and `lastSessionId` | Session `namespace` and `session_id` | Modulo stores navigation preference; Noesis stores run state |
| Plugin-state `item.<feed-hash>` link record | Feed item ID/source version and `workspace_links` in a promoted session | Modulo owns the local link record; Noesis owns source and transition history |
| Feed inbox view and user-triggered triage | Feed item ID/version, unread/decision state, Awareness session revision | Noesis |
| Escalation navigation | `origin` session and source/annotation references in the new mode | Noesis |
| User-authored notes, tasks, calendar blocks, local planning | Optional versioned `workspace_links` on a Noesis handoff | Modulo for edits; Noesis stores only references |
| Acquired source text, publication time, corrections, citations | Versioned feed or Exploration source | Noesis |
| Browser-local `modulo-information-intake-v1` records | `legacy.<collection>.<id-hash>` plugin-state records and a `migration.<source-hash>` report | Modulo; raw user fields and IDs are retained |

The current plugin stores preferences and a versioned Modulo intake-item link when an Awareness item is promoted. It shows up to 50 feed items, supports RSS/Atom and newsletter-feed subscriptions, explicit refresh, separate read state, daily Awareness triage, and promotion into Exploration. Saved keyword signal rules can be previewed with matched terms and excerpts without changing read or decision state. Direct email newsletter ingestion is not yet supported. Exploration can also start without a feed item or project, with a 60-, 90-, or 120-minute time box. Its workbench captures public page URLs and optional readable text, saves feed items without recapture, shows the visited trail and source-version notes, and offers bounded related-source suggestions with visible shared terms. Dismiss/follow, pause/resume, and completion use the supported Noesis session commands. A saved trail source can start a linked Deep Research session while retaining its original source ID and version. This starts the research session; it does not yet build its evidence cards, claims, maps, or brief.

The plugin does not create Modulo item records for unpromoted feed entries or link projects and notes. The full cross-repo object map, stale-reference resolution, correction/retraction propagation, second-device acceptance, and the other native mode journeys remain open. A session export's SHA-256 digest checks integrity but does not authenticate the exporter.

## Decision Support

The plugin can record a standalone yes/no choice without creating a research project. The user enters the question, alternatives, stakes, required confidence, stop condition, uncertainty, optional missing inputs/deadline, selected option, and rationale. Noesis stores the finalized `noesis-decision-v2` record and its revisions; Modulo stores the current decision ID/version and a stable per-decision artifact link in signed-in plugin state. The request key **and exact choice draft** are saved before the create call so a lost response can be retried without a duplicate or a changed payload. A rejected pending create can be abandoned after its outcome is checked; abandoning an uncertain successful call may leave an unlinked Noesis decision. Reload checks current Noesis access, and a denied read hides the record. A revision uses Noesis's expected revision and re-inspects after an uncertain response.

After the Modulo link is confirmed, the plugin starts and completes a Decision Support intake session with a versioned decision reference and the Modulo artifact link. If the current session is Exploration or Deep Research, it records that session as the origin and carries its accessible source references into the decision handoff. The source context is retained in the Modulo link so an interrupted handoff replays against the same origin. The mode commands have deterministic keys, so **Complete mode handoff** can safely retry after an interruption. **Compare options** sends author-supplied utility weights and optional alternative weights to Noesis, then shows ranked/tied options, missing inputs, and a version-pinned sensitivity receipt. It does not infer utilities or acquire evidence. Linking the choice to a Modulo task/project and user-assessed decision quality remain open.

## Problem-Solving

The Information Intake plugin can open a Noesis Problem-Solving session directly from a symptom, environment/version, urgency, and observable success check. If another intake session is active, it records an interrupting origin; Noesis carries that session's Modulo return links. The plugin keeps the current problem session ID in signed-in plugin state and reloads the authoritative Noesis trail after restart. It shows hypotheses, proposed fixes, caller-reported attempts, failed or passed observed checks, and next actions. A proposal cannot resolve the problem; the **Resolve verified problem** action is enabled only after Noesis reports its completion checks met. Pause and resume use the same session ledger.

Start and step keys are saved to plugin state before calls. A pending step can be replayed with its original key, payload, and expected revision after an uncertain response, so a successful remote write is not duplicated. The UI labels attempts as reported; it does not run external fixes or independently evaluate the success check. Direct launch from an arbitrary Modulo task, scoped Blueprint execution receipts, and representative live outcome acceptance remain work under [Noesis #1574](https://github.com/Ikey168/Noesis/issues/1574) and [Modulo #474](https://github.com/Ikey168/Modulo/issues/474).

## Playbooks and guided rehearsals

A completed, verified Problem-Solving session can be promoted into a versioned **draft** Noesis playbook. The editor records prerequisites, environment, ordered actions, expected results, recovery instructions, a final check, and source rationale. It saves the exact draft, source/revision, and stable request or edit key in Modulo plugin state before calling Noesis, so a lost response can be replayed after restart. A rejected pending save can be explicitly abandoned after its outcome is checked; abandoning an uncertain successful call may leave an unlinked Noesis draft. Revision history and the verified problem origin remain in Noesis; saving a revision never marks a playbook trusted.

**Start guided run** pins the playbook revision and rehearsal environment. The plugin reloads that exact revision for an existing run even if the draft is edited later. Each step records a caller-reported pass/fail observation; a failed step stays current for retry, while a passed final check completes the run. A pending result retains its command key, payload, and expected run revision for replay after an uncertain response. Noesis counts completed rehearsals as reported evidence only. The plugin does not execute the actions, grant execution authority, or independently verify outcomes. Trusted promotion, scoped external execution, and live acceptance remain open under [Noesis #1576](https://github.com/Ikey168/Noesis/issues/1576) and [Modulo #474](https://github.com/Ikey168/Modulo/issues/474).

## Retrieval practice

From a current intake session with a versioned Noesis source or concept reference, the plugin can author a one-card retrieval pack with a prompt, author answer, practice kind, and textual mastery criterion. Modulo stores the selected reference and exact draft with a stable key before creating the authoritative Noesis pack. This is authoring, not automatic answer generation or verification.

**Due and overdue** lists Noesis prompts without answers; the review view does not prefetch pack answers. Starting a review saves a retry key in Modulo plugin state and pins the Noesis pack revision. The user records an answer and whether help or notes were used before the author answer can be revealed; a separate self-assessment then updates Noesis's schedule. Each command saves its key, payload, and expected revision before the call so an uncertain response can be replayed after restart. A rejected pack save or review start can be explicitly abandoned after its result is checked; abandoning an uncertain successful call may leave an unlinked Noesis record. Assisted and self-rated results are labeled; the UI does not claim unaided mastery from them. Pack revisions, source correction alerts, practice-plugin migration, and a signed-in live review journey remain work under [Noesis #1577](https://github.com/Ikey168/Noesis/issues/1577) and [Modulo #474](https://github.com/Ikey168/Modulo/issues/474).

## Migrating Modulo's own intake records

The existing **Knowledge → Research Workflow** surfaces use the browser-local `modulo-information-intake-v1` store. Open **Knowledge · Research Workflow data** in the Information Intake plugin on the same browser profile and origin that holds those records. **Preview local intake** reads that key in the browser and refreshes the authenticated Information Intake plugin-state namespace. It counts all twelve version-1 collections, compares stable per-record IDs and content hashes with existing plugin state, flags duplicate URLs and missing local item/project references, and blocks unknown top-level collections, malformed IDs, oversized records, or conflicting remote versions before writing. Raw record objects are retained so user-specific fields are not normalized away. A 20 MB local store and 5,000-record budget bound this path. The Research Workflow editors must read signed-in state before a second device can edit migrated records; this copy and inventory alone do not switch their storage backend.

**Import into plugin state** stages one record per original Modulo ID, then an import report with the source digest, counts, and record keys. The plugin-state client synchronizes those records across signed-in clients and queues writes if connectivity drops after preflight. Repeating the import skips matching records; a changed record requires conflict resolution and a fresh preview. The local browser store is never deleted. **Undo unchanged import** checks the report and rehashes every imported payload before tombstoning records, so it refuses to discard later edits. A later import can restore those tombstones. The UI distinguishes confirmed records from queued writes and conflicts. **Load saved records** shows the imported collections, titles, and original IDs from signed-in plugin state on another device without requiring that device's local browser store. It is a read-only inventory; the Research Workflow surfaces still need to read signed-in state before their editing workflows can continue there. Noesis source/evidence objects are not created from these legacy records merely because they share a URL; linking them requires the native source workflows and an explicit mapping decision.

## Retry and failure behavior

The plugin saves an Awareness start request key in durable plugin state before calling Noesis, then reuses that key if the response is lost. Before promotion, it creates or updates an owner-scoped item-link record in Modulo plugin state, waits for synchronization, and passes its stable ID and object version to Noesis as a return link. It clears the pending key after storing the returned session ID. Item decisions use a command key and expected session revision; after an error the view reloads Noesis state to resolve a possible committed result or revision conflict. Modulo does not cache Noesis source content in plugin state. The backend caps request and response sizes and returns no Noesis credentials. Offline Modulo preference edits use the existing plugin-state queue; Noesis mutations require a live connection and are not queued by this initial plugin.
