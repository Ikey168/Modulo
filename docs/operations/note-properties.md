# Typed note properties

Typed properties are stored separately from the existing string metadata map and tags. Flyway V16 creates definitions and values without converting or deleting legacy data. A property belongs to an owner and has a stable key, title, type, and optional select choices. Types and choices are immutable once defined; use a new key for a different interpretation. Titles use optimistic definition revisions.

Supported values are text, JSON numbers, booleans, ISO dates, UTC instants, select and multi-select choices, HTTP(S) links without embedded credentials, and owned note IDs. Instants normalize to UTC with nine fractional digits so indexed comparisons preserve chronological order. Explicit JSON `null` is stored; an absent key has no row. `set: {key: null}` and `remove: [key]` have distinct meanings. Deleted or transferred note-reference targets read as null; references never expose another owner's note content.

All API calls require an authenticated provisioned account. `/api/note-properties/definitions` supports GET and PUT; a new definition uses revision 0. POST `/read` takes `noteIds` (up to 100). POST `/write` takes `changes`, each containing `noteId`, expected note `version`, a `set` object, and `remove` keys. The batch commits atomically and increments each affected note version. Any stale version, missing owned note, invalid value, or unavailable reference rolls back the whole batch. A 409 `PROPERTY_VERSION_CHANGED` requires reading current values before retrying; clients must not silently overwrite concurrent edits.

POST `/query` takes up to ten AND-combined `filters`, an exclusive note-ID cursor `after`, and `limit` from 1–100. Operators are `eq`, numeric/date/instant `gt`/`gte`/`lt`/`lte`, multi-select `contains`, `exists`, and `missing`. Exists includes explicit null; ordered filters exclude null. Results include note IDs, versions, and typed values. Schema and note ownership constrain every lookup. Composite database ownership constraints and transfer cleanup also protect persisted values.

Property reads, writes, queries, and schema writes create audit events with verified owner attribution. Events omit property values and search terms. Existing note audit access remains owner scoped. The equality/range index starts with owner and property key; multi-select containment also has a JSONB GIN index. `NotePropertyServiceTest` measures PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` against 20,000 rows and asserts the selective equality index path. This is a reproducible regression workload, not a production latency guarantee.

Measured locally on PostgreSQL 16 with the regression fixture: the numeric equality query selected `note_property_range_idx`, returned 20 rows, and executed in 0.150 ms with 26 shared buffer hits. Text equality uses a fixed-size hash index plus an exact JSONB comparison, allowing 4,096-character values without exceeding PostgreSQL B-tree entry limits. Numeric equality retains JSONB numeric comparison (so `2` and `2.0` compare equally). The bounded-value range index avoids indexing large text values.
